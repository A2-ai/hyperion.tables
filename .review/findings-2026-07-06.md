## 1. Architecture summary

`hyperion.tables` is a pure R shared library (67 exports, no executables, no
concurrency) that turns NONMEM model objects from the upstream `hyperion`/`pharos`
toolchain into publication-ready parameter, model-comparison, and run-summary
tables, rendered through two first-class backends (gt and flextable) and exported
to PNG and Word. ~10.4k lines across 22 files.

**Layering (verified).** Three pipelines share one shape:
`apply_* (data.frame + spec in attributes) → make_* (build HyperionTable IR) →
render_to_{gt,flextable} → render_to_{image,word}`. The addendum's repo map is
accurate. I spot-checked and confirmed: `apply_formatting()` (R/render-common.R:13)
is the sole fan-in on every render path and is called only from the two backends
(R/render-gt.R:21, R/render-flextable.R:23); `HyperionTable` is the IR both
backends consume; the six pipeline entry points exist where mapped (one trivial
offset: `apply_table_spec` starts at R/parameter-apply.R:19, not :1). The
`(?)`-marked survey claims all resolved as stated: Windows *is* commented out of
the CI matrix (.github/workflows/R-CMD-check.yaml:23); `apply_gt_hide_cols` *is* a
no-op (Finding LHF); the three `hyperion::`-qualified call sites are absent from
the `@importFrom` manifest but use explicit `::`, so that is benign, not a defect;
`test-name-lookup-omega.R` is literally 0 lines.

**Flows traced.** (a) Parameter happy path: `get_parameters` → `apply_table_spec`
(derive cv/rse/ci, transforms, name resolution, sections) → `add_summary_info`
(attach `model_summary` attr) → `make_parameter_table` → render. (b) Comparison:
`compare_with` (suffixed join, `hyperion_meta` attr) → optional
`add_model_lineage` → `make_comparison_table`. (c) Word export: `render_to_word`
→ `gt::gtsave` → ~15-helper OOXML surgery suite in place → re-zip.

**Structural read.** The core IR boundary is clean and the shared
`apply_formatting`/footnote-builder layer is a genuine strength — it makes gt and
flextable agree on data-level content (CI merge, missing-text, sig-figs, footnote
*content*), which I confirmed cell-by-cell. The structural health problems are
concentrated in three places the addendum correctly predicted: (1) the *rendering*
layer below `apply_formatting`, where the two backends re-implement styling
independently and have drifted; (2) the **column-name string conventions** that
are the de-facto inter-stage contract, encoded independently at ~26 sites with no
shared source of truth and demonstrated prior drift (NEWS 0.5.0); and (3) the
recently-relocated (0.5.0) name-resolution code in `parameter-apply.R`, which has
an empty test file and two silent-corruption bugs sitting in the coverage hole.
Numeric formatting — equally weighted per `[Q9]` — has one defect that fires on
default settings with ordinary pharmacometric data.

## 2. Primary findings (ranked)

### F1 — `format_sigfig_pad` emits scientific notation for |x| ≥ 10^n_sigfig, silently dropping significant figures in every cell
**Severity: Critical · Category: F/numeric-correctness · Confidence: High (reproduced end-to-end)**

**Evidence:** R/variability.R:43-46. `base <- trimws(formatC(x, digits = n_sigfig,
format = "g"))`; if the result contains `e`/`E`, the function `return`s it verbatim,
skipping all the sig-fig padding that is its entire purpose. This is the single
formatter behind every numeric cell: `format_value` / `format_numeric_columns_shared`
(R/render-common.R:258-266), `format_numeric_for_rules` (R/variability.R:11-31),
and CI merge (R/render-common.R:194-220).

**The issue:** `%g` switches to scientific whenever the decimal exponent ≥ digits.
At the default `n_sigfig = 3`: `999.4 → "999"` but `999.5 → "1e+03"` (1 sig fig);
`3497.66 → "3.5e+03"` (2 sig figs); `1234 → "1.23e+03"`. The displayed precision
silently varies from 1 to n, and raw computer notation lands in the cell. Verified
end-to-end: scaling the run001 fixture TVV to 4085.65 L renders the gt HTML cell as
`4.09e+03` and the CI as `[3.5e+03, 4.67e+03]`. The sibling footnote formatter
`hyperion::format_hyperion_sigfig_string(3497.66, 3)` returns `"3500"` (it uses
`format="fg"`), so cells and footnotes of the *same table* disagree in style.

**Blast radius:** Fires on **default settings** with ordinary data — any parameter
≥ 1000 (volumes, AUC-scale thetas, baselines), any RSE/CV% ≥ 1000 (near-zero
estimates; fixture run002 already shows RSE 423 and `(CV = 1.21e+03%)` was
reproduced), CI bounds, tiny pct-changes (`-2e-05`). No vignette or snapshot
exercises values ≥ 1000, so CI is blind to it. This reaches regulatory-adjacent
deliverables with visibly wrong/inconsistent precision.

**Remediation:** Rebase on `trimws(formatC(signif(x, n), digits = n, format = "fg"))`
(matching hyperion), then run the existing padding. Keep an explicit opt-in
scientific threshold for genuine extremes (|x| ≥ 1e6 / ≤ 1e-6) with the mantissa
padded to n digits. **Effort: ~½ day + snapshot regeneration.**

### F2 — Variability rule predicates are evaluated against *stringified* numbers; comparisons are lexicographic and silently wrong
**Severity: High · Category: B/D correctness · Confidence: High (reproduced)**

**Evidence:** R/variability.R:110-113. `build_variability_parameter` calls
`format_numeric_for_rules(data, spec@n_sigfig)` — converting *all* numeric columns
to character — **before** `build_variability` evaluates the rule quosures via
`case_when` (R/variability.R:101-105). Both the LHS conditions and the RHS label
expressions therefore see strings. Same for comparisons (R/variability.R:117-136).

**The issue:** A user rule `cv > 30 ~ "(HIGH)"` becomes the string comparison
`"9.50" > "30"` → TRUE (wrong) and `"120" > "30"` → FALSE (wrong). Reproduced:
`cv = 9.5` labelled HIGH, `cv = 120` labelled normal — inverted. Even the package's
own `default_variability_rules()` (R/spec-classes.R:141-150) is defeated at the
boundary: its `cv != 0` guard becomes `"0.00" != 0`, which coerces to string and
returns TRUE, so a parameter with `cv == 0` renders `"(CV = 0.00%)"` instead of the
intended blank.

**Blast radius:** Any spec with numeric thresholds in `set_spec_variability` (the
DSL invites exactly this) produces silently wrong condition-dependent labels;
default specs are affected only at cv == 0.

**Remediation:** Split each two-sided formula — evaluate the LHS predicate against
the *raw numeric* mask and the RHS label against the *formatted* mask, then combine
via an `ifelse` cascade. **Effort: ~1 day incl. tests.**

### F3 — `resolve_name_columns` uses all-or-nothing name matching; one uncommented parameter silently corrupts `nonmem_name`/`user_name` for every row
**Severity: High · Category: A/D correctness · Confidence: High (reproduced)**

**Evidence:** R/parameter-apply.R:125-138. `match_idx <- match(df$name, rownames(labels));
if (all(is.na(match_idx))) { match_idx <- match(df$name, labels$name) }`. The
NONMEM-name→user-name fallback fires only when *no* row matches the NONMEM names.

**The issue:** Post-0.5.0, `params$name` is the user/comment name, so normally no
row matches `rownames(labels)` and the fallback runs. But if even one parameter
lacks a `$THETA/$OMEGA/$SIGMA` comment, its name *is* its NONMEM name (`"THETA1"`),
that one row matches, `all(is.na(...))` is FALSE, and the fallback never runs.
Every *other* row then gets `NA` and silently falls back to
`nonmem_name = user_name = df$name` (R/parameter-apply.R:130-138). Reproduced with
run001.mod minus one theta comment: `nonmem_name` became `"TVV"`, `"OM1 (TVCL)"`
instead of `"THETA2"`, `"OMEGA(1,1)"`. Compounding this, the `match()` ignores
`kind` (contrast `apply_name_source` at R/parameter-apply.R:536-539, which keys on
`paste(name, kind)`), and the comparison joins have the *same* kind-blind bug
(`full_join(by = "name")` at R/compare.R:481,504,528) — so a THETA and SIGMA
sharing a display name resolve to first-match / cross-pair. Two independent
subsystems, one root cause.

**Blast radius:** Uncommented parameters are routine in draft models. Inline/TOML
section overrides keyed by NONMEM name stop matching (warning only), section rules
and `row_filter` on `nonmem_name` silently select nothing, and
`set_spec_parameter_names(source="nonmem")` degrades — wrong tables ship silently.
This region has *zero* test coverage (F-process below).

**Remediation:** Per-row coalesce of both match vectors and key on `(name, kind)`
in both `resolve_name_columns` and the `compare.R` joins. **Effort: ~1 day incl.
comparison snapshots.**

### F4 — Per-column `display_transforms` silently report statistics on the wrong scale when no kind uses `"all"`
**Severity: High · Category: A/D correctness · Confidence: High (reproduced)**

**Evidence:** R/parameter-apply.R:331-334. `build_display_transforms` appends a
catch-all `dt_kinds[["all"]] <- toupper(names(dt))` whenever no kind declares
`"all"`; `dt_for(col)` (R/parameter-apply.R:50-53) routes any column *not* named in
the spec's per-kind lists to `dt_all`, i.e. "transform for every kind".

**The issue:** `set_spec_transforms(theta="estimate", omega="estimate",
sigma="estimate")` means "transform only the estimate column" — but because no kind
uses `"all"`, cv/rse/ci fall through `dt_for` to `dt_all` and get transformed
anyway. Output is byte-identical to the fully-transformed default (reproduced:
omega `cv/rse/ci` still on the CV/exp scale). Yet the *mixed* case
`theta="all", omega="estimate"` correctly leaves omega cv/rse/ci untransformed. So
the meaning of "which columns to transform" inverts depending on whether some
*other* kind happens to use `"all"` — statistics reported on the wrong scale
(variance vs CV) with no warning.

**Blast radius:** Anyone restricting display transforms per column. The numbers
look plausible but are on the wrong scale — the worst failure mode for a
publication-tables package. Related validator gap: `valid_transform_cols`
(R/spec-classes.R:251-260) accepts `"ci_low"`/`"ci_high"` as transform targets, but
the engine only consults `dt_for("ci")` (R/parameter-apply.R:75-86), so
`set_spec_transforms(omega=c("estimate","ci_low","ci_high"))` yields a transformed
estimate beside an untransformed CI in the same row.

**Remediation:** When no kind declares `"all"`, the fallback must map unlisted
columns to *no* kinds (`dt_kinds[["all"]] <- character(0)`). Remove `ci_low`/`ci_high`
from `valid_transform_cols` or make `dt_for("ci")` honor them. **Effort: ~½ day +
snapshot audit.**

### F5 — Column-name string conventions are the real inter-stage contract: ~26 independent encoding sites, no shared source of truth, demonstrated prior drift, three live defects
**Severity: High · Category: A/change-amplification · Confidence: High**

**Evidence:** The pipelines communicate through column-name conventions — the
`model_1`/`model_2` numeric-suffix scheme, the "which columns are bookkeeping vs
displayable" vocabulary, and CI-column aliases — each re-encoded independently.
`comparison_suffix_columns()` (R/spec-validation.R:60-73) is the one shared
constant but is used only as a *fallback* when the spec is NULL. A representative
sample of the ~26 sites:

| Site | Encodes | Note |
|---|---|---|
| R/compare.R:33 `get_comparison_model_indices` | suffix regex `^(cols)_(\d+)$` | model identity inferred purely from names |
| R/compare.R:313, R/compare-table.R:1104-1110 | variability suffix set `{cv,corr,sd,fixed}` | duplicated verbatim, 2 sites |
| R/compare.R:344 `coalesce_cols` | join whitelist | **omits `transforms`** |
| R/compare-table.R:747 | non-display suffix regex | hardcoded, ≠ the shared constant |
| R/compare-table.R:859-860 | catch-all `_(\d+)$` hider | hides any suffixed col not whitelisted |
| R/parameter-table.R:150-160 vs :454-468 | bookkeeping vocab | re-listed, not shared |
| R/spec-validation.R:76-91 vs :94-105 | CI aliases | **two independent lists** |
| R/format.R:202-234 `detect_table_statistics` | footnote-stat vocab | three conventions in one function |
| R/render-flextable.R:131, R/variability.R:127 | symbol/`_idx` suffix readers | independent regexes |

No test references `comparison_suffix_columns`, `expand_ci_alias`, or
`expand_ci_drop_columns`; consistency rests only on HTML/PNG snapshots of recipes
that stay inside the aligned subset. **Prior drift already shipped** — NEWS.md:45
(0.5.0): "`make_comparison_table()` no longer drops columns when an added model
lacks columns present on the reference model" is exactly this bug class. Three
*currently live* divergences ride on the same root:

- **F5a (Medium):** any suffix-shaped column fabricates a phantom model. After
  `compare_with(p1,p2)`, `cmp$estimate_9 <- 42` renders a third "Model 3" spanner
  with fabricated `N/A (no summary)` footnotes (reproduced). Conversely,
  suffix-shaped columns with unknown bases are silently hidden and non-suffixed
  user columns are silently dropped at the join (R/compare.R:439).
- **F5b (Medium, NEWS-0.5.0 class):** the two CI-alias vocabularies diverge.
  `drop_columns="ci_2"` on a 3-model chain kills the CI *footnote* for all models
  while leaving CI columns visible; `drop_columns="ci_3"` behaves correctly — they
  differ only because `expand_ci_drop_columns` (R/spec-validation.R:94-105)
  hardcodes aliases only up to index 2 and expands to *unsuffixed global*
  `ci_low/ci_high`, while the layout scopes per-model. `drop_columns="ci_1"` on a
  single-model table silently deletes the entire CI (all reproduced).
- **F5c (Medium):** `detect_table_statistics` (R/format.R:202-234) checks
  *unsuffixed* `cv/sd/corr/stderr` (only `ci_(low|high)` and literal `rse_1/rse_2`
  are suffix-aware), so comparison tables displaying `cv_1/cv_2/stderr_1/...` show
  the columns but **omit the CV/SE footnotes and formula equations** the identical
  single-model table includes (reproduced). `transforms` compounds this — it is
  excluded from both `coalesce_cols` and `keep_cols`, so it never survives the join.

**Blast radius:** every future feature touching comparison columns must edit N
unlinked sites or reintroduce the NEWS-0.5.0 defect; F5a-c already produce
phantom/missing content in publication tables.

**Remediation:** one internal vocabulary module — `parse_model_suffix(name) →
(base, idx)`, `suffixed(base, idx)`, single registries for display-base /
bookkeeping / non-display / CI-alias sets — replacing all grep sites; better,
make `hyperion_meta` authoritative for the index→column map at join time so model
identity is never re-inferred from names. **Effort: 3-5 days + snapshot churn.**

### F6 — flextable equation-footnote fallback crashes on every input where `equatags` is absent (regression from a doc-cleanup commit)
**Severity: High · Category: B/F · Confidence: High (reproduced, git-bisected)**

**Evidence:** R/render-flextable.R:553. `flextable::as_paragraph(!!!chunks)`.
`flextable::as_paragraph` is a plain `list(...)` function with no rlang splice
support, so `!!!chunks` parses as triple negation of a list →
`Error in !chunks : invalid argument type` for *every* input. The only caller is
the no-equatags markdown-footnote branch (R/render-flextable.R:424-427), reached
whenever equatags (a Suggests dep, gated by a mere warning at :17-21) is missing.
`git show db78d87` ("fixed documentation around ... for setters") rewrote the
working `do.call(flextable::as_paragraph, chunks)` into the splice form.

**The issue:** On any install with flextable but without equatags, rendering any
table with an equation footnote — i.e. every default parameter/comparison table,
since `build_equations_footnote` always emits the CI formula — aborts with an
inscrutable error instead of the intended plain-text fallback. CI never catches it
(equatags is present there), and the entire fallback path (including the three
hard-coded gsub patterns at :509-524 and `parse_subscripts_to_chunks`) is
dead-on-arrival.

**Blast radius:** minimal/air-gapped installs crash on the flagship
`make_*_table(..., output="flextable")`; the whole plain-text footnote path has
zero effective coverage.

**Remediation:** revert to `do.call(flextable::as_paragraph, chunks)` (or
`as_paragraph(list_values = chunks)`); add a test that mocks equatags absent.
**Effort: 1 line + 1 test.**

### F7 — flextable Word export of sectioned tables renders at 1–2 pt (unreadable); the failure is on the package's canonical recipe
**Severity: High · Category: E/F · Confidence: High (reproduced end-to-end)**

**Evidence:** R/render-flextable.R:59 (`autofit`), :114
(`width(ft, j = group_col, width = 0.01)`), :718 (`fit_to_width(max_width = 7)`).

**The issue:** `create_grouped_flextable` correctly pins the section column to
0.01 in, but `render_to_flextable` then calls `flextable::autofit()` *afterwards*
(:59), which re-measures that column from the full merged section label
("Interindividual covariance parameters" → 3.39 in), inflating the table to
~12.7 in. `render_to_word.flextable` then calls `fit_to_width(7)`, which fits by
*shrinking fonts*: 11 pt → 2 pt for the parameter table, and for the comparison
table flextable aborts with "results in negative font sizes" and ships an unfitted
~12 in table on a portrait page. Reproduced: the produced `param-ft.docx` has 178
runs at 2 pt; `cmp-ft.docx` has 251 runs at 1 pt. Without `set_spec_sections` the
fit lands at a readable 8 pt — so the failure is exactly on the sectioned recipe
used in every test and vignette.

**Blast radius:** every flextable `.docx` deliverable for a sectioned
parameter/comparison table — the mainstream Word output for that backend. Only
symptom is a warning users won't connect to the output.

**Remediation:** re-apply the 0.01 in group-column width after `autofit` (or
autofit data columns only), and replace font-scaling with proportional
column-width scaling (`width(ft, width = dim(ft)$widths * 7/sum(...))`); add a
docx regression test asserting a minimum font size. **Effort: a few hours.**

### F8 — The `sanitize_gt_docx` OOXML suite degrades to silent no-ops under gt/pandoc drift, with nothing asserting its invariants
**Severity: High · Category: E/evolutionary · Confidence: High**

**Evidence:** R/render-gt.R:429-1052; `grep render_to_word tests/` → zero hits;
the only CI exercise is a vignette assertion of `file.exists(word_path)`
(vignettes/table-rendering.Rmd), true whether or not sanitization happened. The
~15 helpers are keyed to exact OOXML shapes the installed gt/pandoc versions emit,
and almost all degrade to a **silent no-op** on a shape change rather than erroring:
`add_vertical_borders` (:581-609) keys on `w:tblHeader` + `w:gridSpan` (missing
tblHeader → border bisects header silently; attr rename → all borders dropped);
`bold_header_rows` (:648-668, unbolded headers); `strip_seq_table_field`
(:675-709, "contains fields" prompt returns); `set_word_compat_mode` /
`set_landscape_orientation` (:470-546, user asks landscape, silently gets
portrait); `fix_caption_style` (:552-560, "unreadable content" prompt returns).
Only the entry-point `read_xml` (:435-436) hard-errors.

**The issue:** a routine gt or pandoc upgrade quietly reintroduces Word-repair
prompts, unbolded headers, wrong orientation, and field warnings into client
`.docx` files; the first person to notice is the client opening the document. I
confirmed the present output is *good* (see What's Good) — the risk is entirely
drift, and there is no tripwire.

**Blast radius:** every gt→Word deliverable, on the next dependency bump.

**Remediation:** a structural docx fixture test (unzip → assert parses, `tblGrid`
present, zero `fldChar`, header runs bold under `tblHeader`, `oMath` count > 0,
single `xmlns:w`, compat15, correct `pgSz`); all pass today, so it is cheap to
snapshot. Add precondition warnings inside helpers (e.g. warn if `segment_lengths`
is set but no `tblHeader` row is found). **Effort: 1-2 days.**

### F9 — An `NA` transform from a name collision crosses the API as a cryptic Rust panic that kills the whole pipeline
**Severity: Medium · Category: B/F · Confidence: High (reproduced)**

**Evidence:** R/parameter-apply.R:54-57. `transforms_vec <- get_parameter_transform(
info, params$name, params$kind)` is passed unguarded into
`compute_cv`/`compute_rse`/`compute_ci`/`transform_value` (:68-87).

**The issue:** With a THETA commented `"Additive"` alongside a SIGMA named
`"Additive"` (an ordinary NONMEM idiom for additive-error parameters),
`hyperion::get_parameter_transform` returns `NA` for the theta even though `kind`
is passed. `apply_table_spec` then dies inside `dplyr::mutate` with
`Caused by error in compute_cv(): ! NA transform at index 2` — no parameter name,
no hint, whole table lost (reproduced on a modified run001.mod). The underlying
kind-blind lookup is arguably a hyperion bug (see Questions), but this package
should not surface it as a raw Rust index error.

**Blast radius:** any model where a theta shares a display name with an
omega/sigma comment; the flagship exported function fails unactionably.

**Remediation:** coalesce `NA` transforms to `"identity"` with a warning naming the
parameter; file the kind-qualified NA upstream. **Effort: ~2 hours here.**

### F10 — `compare_with()` chaining after `add_model_lineage()` silently drops `lineage`, removing all LRT footnotes and mis-blaming the user
**Severity: Medium · Category: B/D · Confidence: High (reproduced)**

**Evidence:** R/compare.R:599-635 (`finalize_comparison`) rebuilds `hyperion_meta`
on the attribute-free join result and writes exactly four fields — `summaries`,
`labels`, `table_spec`, `pct_change_refs` — never copying the fifth documented
field, `lineage` (written by `add_model_lineage` at R/compare.R:726; inventory at
R/df-attrs.R:33-35 says "five pieces"). `pct_change_refs` *is* explicitly merged
from `params1` (:608-613), proving carry-forward was the intent.

**The issue:** In the order lineage-then-chain
(`compare_with(p1,p2) |> add_model_lineage(l) |> compare_with(p3)`), the internal
meta rebuild loses lineage. Reproduced: the chained table has 0 LRT footnote lines
(vs 3 when lineage is re-added afterwards), plus a misleading
`inform`: "LRT suppressed … no lineage attached" (R/compare-table.R:274-283) — the
user *did* attach it. Both chaining and `add_model_lineage` are exported, documented
API with no stated ordering constraint.

**Blast radius:** every chained comparison built from a lineage-carrying comparison
renders without LRT footnotes and without error — wrong-by-omission
regulatory-adjacent output, with the console message blaming the user.

**Remediation:** seed meta from the source before the field writes when chaining:
`if (positions$is_comparison) attr(comparison,"hyperion_meta") <-
get_comparison_meta(params1)` (the four subsequent writes overwrite what must be
recomputed; lineage rides along). **Effort: ~3 lines + 1 regression test.**

crash `apply_table_spec` with a raw `vapply` type error at R/parameter-apply.R:365
and :424-432 (Medium-High). **`n_decimals_ofv = NA`** is validated as legal
(R/spec-validation.R:223-242) but crashes summary rendering at R/render-common.R:147

(`models=` on TableSpec, `parameters=`/`file=` on SummarySpec) via `drop_named_dots`

## 5. What's good (preserve while fixing the above)

- **Single shared data-formatting layer.** `apply_formatting` plus the footnote
  builders run once before the backends fork, so gt and flextable agree on CI
  merge, missing-text, sig-figs, and footnote *content* — verified cell-by-cell,
  and it is why the numeric cross-pipeline drift hypothesis was *refuted* (a
  parameter table and the same model's comparison column agree 8/8). This is the
  right seam; the drift lives strictly *below* it, in per-backend styling. Keep the
  seam and push more of the styling contract through it.
- **S7 spec validators with friendly-error translation.** The
  `with_section_options_error` layer (R/spec-setters.R) turns deep S7 validation
  failures into actionable messages; `resolve_section_meta`/`apply_section_meta`
  ordering, repeated/out-of-order calls, and keep+exclude conflicts all behave
  correctly (swept, nothing found). The data-side input (`params`) deserves the
  same care (F-Low).
- **Clean lifecycle/env hygiene in the export paths.** `QUARTO_BIN_PATH` and the
  `zip_dir_contents` `setwd` are both `on.exit`-restored and survive induced errors
  (the addendum's env-safety hypothesis was refuted); temp dirs and intermediate
  HTML are cleaned even on mid-sanitize failure. The gt→Word OOXML output is
  genuinely sound today (parses, bolded headers, real OMML, intact footnotes,
  correct landscape) — F8 is about *guarding* that, not fixing it.
