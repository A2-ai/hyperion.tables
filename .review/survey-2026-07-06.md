## 1. Repository map

### Purpose and type

`hyperion.tables` is an R package (shared library, no executables) that produces
publication-ready tables — parameter tables, model comparison tables, and run
summary tables — from NONMEM pharmacometric models managed by the upstream
`hyperion`/`pharos` toolchain (both A2-Ai internal). Output targets are `gt` and
`flextable` table objects, exportable to PNG and Word (`.docx`). Version
0.5.0.9000, ~10.4k lines of R across 22 files, repo started 2026-01-23
(~6 months old, 167 commits).

### Entry points (exported API; no mains/routes/workers)

Three data pipelines, each `apply → (enrich) → make_* → render`:

- **Parameter pipeline**: `apply_table_spec()` (`R/parameter-apply.R:1`) →
  `add_summary_info()`, `make_parameter_table()`, `get_table_spec()`
  (`R/parameter-table.R`).
- **Comparison pipeline**: `compare_with()`, `add_model_lineage()`
  (`R/compare.R`) → `make_comparison_table()` (`R/compare-table.R:432`).
- **Summary pipeline**: `apply_summary_spec()`, `make_summary_table()`,
  `get_summary_spec()`, `summary_filter_rules()` (`R/summary.R`).
- **Rendering**: `render_to_gt()` (`R/render-gt.R:12`), `render_to_flextable()`
  (`R/render-flextable.R:12`), shared preprocessing `apply_formatting()` plus
  S3 generics `render_to_image()`/`render_to_word()` (`R/render-common.R:13,349,382`)
  with backend methods in the two render files.
- **Spec construction**: `TableSpec`/`SummarySpec` S7 classes
  (`R/spec-classes.R:194,503`), option classes `CIOptions`/`ParameterNameOptions`/
  `SectionOptions` (`R/spec-options.R:24,121,170`), ~20 `set_spec_*` setters
  (`R/spec-setters.R`) and ~20 `get_spec_*` getters (`R/spec-getters.R`),
  rule DSLs `section_rules()`/`filter_rules()`/`variability_rules()`
  (`R/spec-rules.R`).
- **Load hook**: `.onLoad` → `S7::methods_register()` (`R/zzz.R`).

NAMESPACE: 67 exports, 6 S3 methods (`render_to_image`/`render_to_word` ×
default/gt_tbl/flextable).

### Intended layering (inferred)

specs (S7 value objects) → pipeline stage 1 (`apply_*`: plain data.frame + spec
carried in attributes) → pipeline stage 2 (`make_*`: build `HyperionTable` IR) →
backend renderers (`render_to_gt`/`render_to_flextable`) → exporters
(`render_to_image`/`render_to_word`). Inferred from the `Collate:` order in
`DESCRIPTION`, `@include` directives (`R/hyperion-table.R:1`), and the
`HyperionTable` doc comment ("Captures all styling intent in a format-agnostic
way", `R/hyperion-table.R:8-11`). The IR boundary is mostly respected; the main
leak is gt-specific docx state stashed as
`attr(gt_table, "hyperion_segment_lengths")` (`R/render-gt.R:82`, read back at
`R/render-gt.R:409`).

### Most load-bearing files

1. `R/render-common.R` — `apply_formatting()` sits on every render path for all
   three table types; also owns the export generics.
2. `R/hyperion-table.R` — the IR class every `make_*` produces and both backends
   consume; its property list is the de facto renderer contract.
3. `R/spec-classes.R` — every pipeline call consumes a `TableSpec`/`SummarySpec`;
   validators here gate all user configuration.

### Cross-cutting concerns

- **Errors**: rlang throughout. De facto strategy: `abort` on spec-type
  mismatch, missing spec at `make_*` time, and empty results
  (`R/parameter-table.R:260`, `R/summary.R:76,283`, `R/compare-table.R:406-411`,
  `R/compare.R:258`); `warn`-and-continue for per-model failures in the summary
  pipeline (`R/summary.R:277-294`, back-fills NA rows); `inform` for statistical
  suppression (`R/compare-table.R:274`, `R/summary.R:660`). Suggests-gating via
  `check_suggested()` (`R/utils.R:23`) with mixed abort/warn severities.
- **Config**: no package-level options. `getOption("knitr.in.progress")` read in
  both image renderers (`R/render-gt.R:351`, `R/render-flextable.R:662`);
  `QUARTO_BIN_PATH` env var unset/restored around katex rendering
  (`R/render-gt.R:359-363`); path resolution delegated to
  `hyperion::from_config_relative` (`R/compare.R:137`, `R/summary.R:271`); tests
  set `options(hyperion.config_dir = ...)` (`tests/testthat/setup.R`).
- **Logging**: none (only rlang conditions).
- **Validation**: three layers — S7 validators embedded in classes
  (`R/spec-classes.R:70,249,550`; `R/spec-options.R`), free-function helpers
  (`R/spec-validation.R`), and imperative constructor checks plus
  friendly-error translation in setters (`R/spec-setters.R:442-489`).
- **Concurrency**: none; pure single-threaded data transformation.
- **Inter-stage state**: data.frame attributes — `hyperion_spec`,
  `model_summary`, `.needs_dofv`, `summary_time_unit`, `hyperion_meta`
  (partially centralized in `R/df-attrs.R`; hand save/restore around dplyr verbs
  at `R/compare.R:12-30` and `R/summary.R:114-118`).

### Build / test / CI

Dependency management is **rv** (A2-Ai's package manager): `rproject.toml` pins
R 4.5, private `prism`/`hyperion-eco` repositories, and `hyperion` at git tag
v0.5.0 (`DESCRIPTION` says `hyperion (>= 0.5.0)`). CI
(`.github/workflows/R-CMD-check.yaml`): R-CMD-check on macOS R4.5 + Ubuntu
R4.2–4.5, no Windows, requires `PRIVATE_REPO_ACCESS_TOKEN`. Tests: testthat
edition 3, ~4.2k lines; snapshot strategy is paired HTML (normalized, runs
everywhere) + PNG via webshot2 (skipped on CI, Windows, and Linux —
`tests/testthat/helper-table-snapshots.R:11-13,46-48` — so the ~74 committed
PNGs only regenerate on local macOS). Release: tag-triggered multi-platform
binary builds published to GitHub Releases (`.github/workflows/r-release.yml`,
still contains template FIXME/TODO scaffolding).

## 2. Risk hypotheses (ranked)

### H1 — The summary and comparison pipelines compute LRT degrees of freedom differently, producing potentially different p-values for the same model pair

- **Hypothesis**: `calculate_dofv` (summary) and `can_show_lrt`/
  `format_ofv_lrt_footnote` (comparison) are independent implementations of the
  same statistical test that have drifted: summary uses the *signed* difference
  of total parameter counts from `summary()` and only reports when positive
  (`df_calc <- as.integer(model_npar - parent_npar)`; `df_calc > 0` gate,
  `R/summary.R:684-689`), while comparison counts non-fixed parameter rows from
  the joined `fixed_<idx>` columns and takes the *absolute* difference
  (`k1/k2 <- sum(!is.na(fixedN) & !fixedN)`; `df <- abs(k2 - k1)`,
  `R/compare.R:122-124` and duplicated at `R/compare-table.R:241-243`).
- **Signal**: confirmed by direct read of both implementations; the shared
  primitive `lrt_pvalue()` (`R/utils.R:106`) is common but df sourcing and sign
  conventions are not. Fixed parameters and same-total-different-fixed model
  pairs will produce different df between the two tables.
- **If true, cost**: a run-summary table and a comparison table in the same
  report can show different (or differently-suppressed) p-values for the same
  parent/child pair. For a pharmacometrics deliverable this is a
  correctness/credibility problem, not a style problem.
- **Investigation sketch**: diff `R/summary.R:616-695` against
  `R/compare.R:91-135` + `R/compare-table.R:192-280` clause by clause (df
  source, sign, obs-count gate, lineage gate, suppression vs NA behavior).
  Construct a fixture pair from `inst/extdata/models/onecmt` where a parameter
  is fixed in one model (e.g. run002 variants) and compare emitted df/p-value
  through both pipelines. Also check the df duplication *within* the comparison
  side (`compare.R` vs `compare-table.R` compute k1/k2 twice).
- **Confidence**: high.

### H2 — The gt and flextable backends are parallel independent implementations of the same styling semantics with no conformance mechanism, and the LaTeX handling has already trifurcated

- **Hypothesis**: every styling concern is implemented twice with no shared
  logic or cross-backend test, so the two outputs drift; LaTeX/markdown handling
  exists three times (gt HTML via `gt::md()`/katex, gt docx via a hand-rolled
  LaTeX→OMML rewriter, flextable via a hand-rolled chunk parser) and already
  disagrees at the edges.
- **Signal**: 1:1 parallel helper pairs — labels (`R/render-gt.R:136` vs
  `R/render-flextable.R:227`), spanners (`:172` vs `:266`), bold (`:185` vs
  `:313`), borders (`:220` vs `:350`), footnotes (`:236` vs `:401`), title
  (`:161` vs `:332`). LaTeX paths: `rewrite_latex_to_omml`
  (`R/render-gt.R:883`) vs `convert_md_label`/`parse_subscripts_to_chunks`
  (`R/render-flextable.R:249,561`). `build_footnote_paragraph` matches three
  exact full-formula strings by `gsub` (`R/render-flextable.R:509-524`) that
  must stay in sync with the footnote text emitted by `format.R` builders —
  wording drift silently falls through to plain text. Comparison model borders
  implemented three times (`R/render-gt.R:68-83`, `R/render-gt.R:581` for docx,
  `R/render-flextable.R:360-380`).
- **If true, cost**: the same spec renders differently depending on backend;
  every new styling feature must be written 2–3 times; regressions appear only
  in whichever backend the author didn't test (snapshots exist per-backend but
  nothing asserts equivalence).
- **Investigation sketch**: build one feature-rich `HyperionTable` (sections +
  spanners + borders + `$...$` in labels and footnotes + missing-text + CI
  merge) and render through both backends; diff semantic content. Grep the
  emitted footnote strings from `R/format.R` (`build_equations_footnote`) and
  `R/compare-table.R` (`format_ofv_lrt_footnote`) against the hard-coded gsub
  patterns at `R/render-flextable.R:509-524` for drift that has already
  happened.
- **Confidence**: high (existence certain; the open question is how much
  observable drift there is today).

### H3 — The Word/image export path is the most intricate code in the package and has zero test coverage

- **Hypothesis**: `render_to_word.gt_tbl` and its ~15-helper OOXML sanitizer
  suite (`sanitize_gt_docx`, raw `xml2` surgery, zip repacking, LaTeX→OMML via
  equatags, `R/render-gt.R:402-1052`) plus `render_to_image` (webshot2,
  `QUARTO_BIN_PATH` env juggling at `R/render-gt.R:359-363`) harbor latent
  failure modes because nothing exercises them.
- **Signal**: zero references to `render_to_word` or `render_to_image` anywhere
  in `tests/testthat/` (confirmed by the test survey); the docx path depends on
  exact OOXML shapes produced by the installed gt version (`<w:tblHeader/>`
  detection, gridSpan walking, `R/render-gt.R:591-605`); env-var manipulation is
  a process-global side effect.
- **If true, cost**: client-facing Word deliverables silently malformed or
  export crashes on a gt/officer/equatags version bump; nothing in CI would
  notice.
- **Investigation sketch**: read `sanitize_gt_docx` and helpers for partial-
  failure handling (tempdir cleanup, zip failure mid-write, missing XML nodes →
  what happens on a gt version change); verify `QUARTO_BIN_PATH` is restored on
  error paths (is it wrapped in `on.exit`?); run `render_to_word` on a fixture
  table for both backends and inspect the docx; check
  `render_to_image` behavior when webshot2/Chrome is absent.
- **Confidence**: high that the gap exists; medium that a live bug is found.

### H4 — Attribute-carried pipeline state is a convention-not-mechanism contract that silently degrades under ordinary dplyr use

- **Hypothesis**: the pipeline contract lives in data.frame attributes
  (`hyperion_spec`, `model_summary`, `hyperion_meta`, `summary_time_unit`,
  `.needs_dofv`) which base-R/dplyr operations strip; the codebase hand-manages
  this with save/restore pairs, and any missed pair — internal or in user code
  between pipeline stages — loses state silently (footnotes, labels, lineage,
  LRT gating disappear without warning).
- **Signal**: `capture_comparison_attrs`/`restore_comparison_attrs`
  (`R/compare.R:12-30`) called defensively around `dplyr::select` at
  `R/compare-table.R:479-490` and `:1100-1149`; `summary_time_unit` manually
  saved/restored around `select_output_columns` (`R/summary.R:114-118`); the
  comment at `R/df-attrs.R:33-35` documents the hazard. Only `hyperion_spec`
  loss is loud (`get_table_spec` aborts, `R/parameter-table.R:123`);
  `model_summary` loss is silent (footnote just vanishes,
  `R/parameter-table.R:8`).
- **If true, cost**: user does `params |> apply_table_spec(...) |>
  add_summary_info(...) |> dplyr::filter(...) |> make_parameter_table()` and
  gets a table with no summary footnote and no error; internal refactors that
  add a dplyr verb reintroduce the bug class indefinitely.
- **Investigation sketch**: enumerate every dplyr/base verb applied to
  attribute-carrying data frames between attach and read points across the
  three pipelines; check which attrs survive each; check what the vignettes
  (`vignettes/*.Rmd`) tell users to do between stages; assess whether a
  restore-pair is missing today (esp. in `R/summary.R` around
  `filter_unrun_rows`/`format_time_columns`).
- **Confidence**: medium-high (mechanism certain; live instance unknown).

### H5 — The upstream `hyperion` boundary is a silent-NA contract: renamed or missing summary fields degrade to NA instead of failing

- **Hypothesis**: the shape of `summary(mod)` (`$run_details`,
  `$minimization_results`, `$parameters`, `$run_name`, `$model_file`) and of
  `get_parameters()` columns is a hard cross-package contract enforced nowhere;
  `safe_summary_field()` (`R/utils.R:90`) converts any missing field to NA, and
  `build_summary_df` back-fills NA rows on summary failure, so upstream drift
  shows up as silently empty table cells rather than errors.
- **Signal**: `safe_summary_field` used throughout `R/summary.R`,
  `R/compare.R:348,390`; hyperion functions reached both via the `@importFrom`
  manifest (`R/hyperion.tables-package.R`) and via ad-hoc `hyperion::` calls not
  in the manifest (`hyperion::from_config_relative`, `R/compare.R:137`;
  `hyperion::format_hyperion_decimal_string`, `R/parameter-table.R:27`);
  version pinning differs between `DESCRIPTION` (`>= 0.5.0`) and
  `rproject.toml` (exact tag v0.5.0).
- **If true, cost**: a hyperion minor release renames a summary field and every
  downstream report shows blank OFVs/condition numbers with no diagnostic;
  discovered by a human reading a deliverable.
- **Investigation sketch**: inventory every field name read off `summary()`
  output and every column expected from `get_parameters()`
  (`R/summary.R:build_summary_df`, `R/parameter-apply.R:compute_derived_columns`);
  determine which have any validation; assess whether a single
  validate-summary-shape chokepoint is feasible; check what the tests would
  catch (fixtures are static JSON/ext files in `inst/extdata`, so they can't
  detect live-hyperion drift).
- **Confidence**: medium.

### H6 — The inter-stage column-name conventions (`<base>_<idx>` suffixes, internal-column lists) are re-encoded in many places and have already caused one released bug

- **Hypothesis**: the real stage contract is column-name strings — suffix
  regexes like `"^(...)_(\\d+)$"` (~a dozen sites, e.g. `R/compare.R:33`,
  `R/compare-table.R:746,859`), internal-column lists re-listed independently
  (`R/parameter-table.R:150` vs `R/compare-table.R:745`), symbol/fixed/CI
  column regexes (`R/render-flextable.R:131`, `R/format.R:86,220`) — with no
  central definition, so additions drift.
- **Signal**: NEWS 0.5.0 already records "make_comparison_table() no longer
  drops columns when an added model lacks columns present on the reference
  model" (`NEWS.md:45`) — the drift class firing once; two independent CI-alias
  expansion lists exist (`expand_ci_alias` `R/spec-validation.R:76` vs
  `expand_ci_drop_columns` `R/spec-validation.R:99` with extra aliases
  `ci_1/ci_2/ci_left/ci_right`).
- **If true, cost**: every new column type requires synchronized edits across
  4–6 files with no mechanism; missed sites drop or leak columns silently.
- **Investigation sketch**: grep all suffix regexes and internal-column lists;
  build the cross-reference table; check `comparison_suffix_columns()`
  (`R/spec-validation.R`) against the columns `compare_with` actually suffixes;
  test adding a model with an extra `dt_*` column.
- **Confidence**: medium-high.

### H7 — Section handling is implemented three times (parameter vectorized, summary row-wise, lookup-file overrides) with duplicated warning logic and likely semantic drift

- **Hypothesis**: `build_section` (vectorized `case_when`,
  `R/parameter-apply.R:341`) and `build_summary_section` (row-by-row loop for
  list-column `tags`, `R/summary.R:369`) plus `apply_lookup_section_overrides`
  (`R/parameter-apply.R`) implement the same rule→label semantics separately;
  multi-match warnings, NA handling, and ordering differ subtly between them.
- **Signal**: duplication confirmed by read; NEWS 0.3.0 records a duplicate-
  label crash fixed in this area once already (`NEWS.md:77`); ordering invariant
  in the section setters — `SectionOptions` rebuilt with `order = NULL, filter
  = list()` then meta re-applied afterward (`R/spec-setters.R:548,592,528`) —
  couples two methods that must stay in lockstep.
- **If true, cost**: same rules produce different grouping/warnings in
  parameter vs summary tables; section features (order, filter, assignments)
  added to one pipeline don't reach the other.
- **Investigation sketch**: diff the two builders' semantics on: NA/no-match
  rows, multi-match same-label vs different-label, factor level ordering,
  filter warnings (`R/parameter-apply.R:203,218` vs the summary equivalents);
  check the `apply_section_meta` ordering invariant survives both
  `set_spec_sections` methods (`R/spec-setters.R:534,566`).
- **Confidence**: medium.

### H8 — Spec-layer defaults and boilerplate are duplicated in ways that will drift (property defaults vs constructor signatures; per-class getter/setter copies)

- **Hypothesis**: defaults are stated twice (S7 property `default=` and
  constructor signature — e.g. `n_sigfig = 3` at `R/spec-classes.R:51`, `:364`,
  and `:615`; `hide_empty_columns` at `:47/:360/:614`) and ~20 getters/setters
  are plain functions with repeated `S7_inherits` boilerplate rather than
  generics, so TableSpec/SummarySpec behavior diverges by copy-paste entropy.
- **Signal**: cited lines confirmed; `set_spec_sections` has two near-identical
  S7 methods (`R/spec-setters.R:534` vs `:566`); `default_columns`/
  `allowed_footnotes` duplicated per subclass (`R/spec-classes.R:226,242` vs
  `:531,545`).
- **If true, cost**: a default changed in one place but not the other yields
  different behavior for `TableSpec()` vs `spec@prop <- x` paths; API drift
  between the two spec types (one such inconsistency already visible:
  `get_spec_section_filter(spec)` lacks the `...` every sibling getter has,
  `R/spec-getters.R:229`).
- **Investigation sketch**: table every property's default across (property,
  TableSpec ctor, SummarySpec ctor); grep for behavioral divergence between the
  paired setter methods; low effort, mostly mechanical.
- **Confidence**: medium-low (real but contained; ranked last accordingly).

## 3. Questions for the maintainer (max 10)

Each with the default I'll proceed with if unanswered.

- **Q1 → H1.** Summary tables compute LRT df as the signed total-parameter-count
  difference from `summary()` (`R/summary.R:684`), while comparison tables count
  non-fixed parameter rows and take the absolute difference
  (`R/compare.R:122-124`). Is that an intentional statistical convention
  difference between the two table types? **Default**: accidental drift — treat
  as a correctness target.
- **Q2 → H2.** Are gt and flextable meant to be at feature/visual parity, or is
  gt primary and flextable best-effort? **Default**: parity intended (README and
  vignettes present both equally); drift is in scope.
- **Q3 → H3.** Is Word (`render_to_word`) output a production, client-facing
  deliverable path, or a convenience? **Default**: production deliverable — the
  untested OOXML sanitizer is a priority target.
- **Q4 → H4.** Are users expected to be able to run dplyr verbs (filter, select,
  mutate) on the data frames between pipeline stages (e.g. between
  `apply_table_spec()` and `make_parameter_table()`)? **Default**: yes — they're
  plain data frames and the API shape invites it, so silent attribute loss is in
  scope.
- **Q5 → H5.** Is `hyperion` released in lockstep with this package by the same
  team, and is "missing summary field → NA cell" the intended degradation
  (vs. aborting)? **Default**: lockstep but unenforced; silent-NA is in scope as
  a trust-boundary issue.
- **Q6 → H7.** Summary section rules evaluate row-by-row (for list-column
  `tags`) while parameter section rules are vectorized — is the *mechanism*
  split intentional, with only semantic drift (warnings, NA handling, ordering)
  worth reviewing? **Default**: mechanism intentional (NEWS 0.3.0 documents the
  row-wise rationale); only semantic drift in scope.
- **Q7 → parking lot / targeting.** `render_gt_summary_table` (`R/summary.R:846`),
  `render_gt_comparison_table` (`R/compare-table.R:534`), `apply_model_spanners`
  (`:1046`), `apply_comparison_footnotes` (`:1060`), and
  `convert_footnote_to_text` (`R/render-flextable.R:607`) have no callers — dead
  remnants of the pre-HyperionTable architecture, safe to treat as deletable
  rather than review them? **Default**: dead code; flag for deletion only.
- **Q8 → H3.** PNG snapshots are skipped on CI, Windows, and Linux
  (`tests/testthat/helper-table-snapshots.R:11-13`), so they only regenerate on
  a local mac. Accepted webshot2-flakiness tradeoff? **Default**: accepted —
  Pass 2 won't flag the skip itself, only the resulting zero coverage of export
  paths.
- **Q9 → targeting.** Which matters more right now: statistical correctness of
  the comparison/summary computations, or maintainability of the render layer?
  **Default**: correctness.
- **Q10 → scope.** `rproject.toml` pins `hyperion` at exact tag v0.5.0 while
  `DESCRIPTION` allows `>= 0.5.0` — is rv the single source of truth for dev
  environments, making the DESCRIPTION bound nominal? **Default**: yes — out of
